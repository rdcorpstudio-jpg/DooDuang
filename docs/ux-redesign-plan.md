# แผน UX — ใช้เส้นทางนำร่องเป็นต้นแบบ

ขอบเขตงาน: โฟลเดอร์ DooDuang-v3 สาขา `feat/ui-v3` เท่านั้น ไม่แตะ `main` / `feat/ui-v2`

สภาพแวดล้อม: เครื่องท้องถิ่น / preview เท่านั้น ไม่ยิง Stripe จริง ไม่แก้ข้อมูล production ไม่ push / ไม่ deploy เอง

เอกสารนี้คือแผนที่อนุมัติล่าสุดหลังทำนำร่องและตรวจจากหน้าเว็บที่ render จริง  
**ยังไม่ใช่ใบอนุญาตเริ่ม batch ถัดไป** — รออนุมัติ batch และ event schema ก่อนแก้หน้าอื่น

## สถานะนำร่อง (ทำแล้ว — เป็นต้นแบบ)

เส้นทางที่อนุมัติและทำแล้ว:

1. `/` first-run — จอเดียว ซ่อนแท็บ ปุ่ม `ดูคำทำนาย` → `/choose` เลือกเรื่อง → `/reading?topic=` เพศ วันเกิด ชื่อเล่น (CTA `ดูคำทำนายของ…`) → `/login` หัวข้อตามเรื่องที่เลือก → เรื่องที่เลือก
2. `/reading` — กรอกเพศ วันเกิด ชื่อ (ฟิลด์บังคับเท่าเดิม) รอหลังมีผลอย่างน้อย 1.4 วินาที
3. `/premium` — Explore hub: ทักทาย + ดวงวันนี้ + การ์ดงานกดครั้งเดียว + ไพ่/เมนู
4. เปิดเรื่องผ่าน URL จริง (`/reading/aspect?id=…` หรือ `/reading/tarot`)

กติกาที่ตรวจแล้วและต้องทำซ้ำในทุกหน้า:

- Mae navy `#101827` / ทอง `#d5b16f` / ข้อความ `#f7f4ec` · `#9aa3b2`
- Sarabun เนื้อหา, Srisakdi หัวข้อ
- การ์ดมุม ~18px เส้นทองบาง พื้น navy
- ปุ่มหลัก `.mae-gold-cta` แคปซูล สูงอย่างน้อย 44px ชื่อเป็นกิริยา ไม่ใช้ «ดูเพิ่มเติม»
- ไม่จำลองกรอบ iPhone / status bar / รอยบาก
- เดสก์ท็อปไม่ล็อกทั้งไซต์ที่ 480px — เนื้อหาอยู่ในคอลัมน์อ่านสบาย (`max-w-3xl` หรือคอลัมน์ข้อความแคบกว่า)
- จอแรก: คอลัมน์ข้อความ `max-w` 22–28rem จัดกลาง ไม่ยืดหัวข้อเต็มความกว้างจอ
- **ห้ามทะลุกรอบมองเห็น** — ปุ่มหลัก/ชื่อแบรนด์ต้องเห็นครบใน `visualViewport` ไม่พึ่งสกroll บนจอเดียว ไม่ชิดขอบล่างที่ 0
- หัวข้อไทย `line-height` ≥ 1.45 ไม่ตัดสระ
- ไม่มีแท็บบน `/` · มีแท็บบน `/premium` `/menu` `/dashboard`
- ซ่อนแท็บบน `/premium/pay` / auth / admin / คีย์บอร์ดเปิด
- ผู้มีวันเกิด+ชื่อเปิด `/` แล้วยัง `replace` ไป `/premium`
- กดครั้งเดียวถ้าแตะแรกไม่เพิ่มข้อมูล — ไม่ทำสองแตะเพื่อโชว์ปุ่มกลางถ้าการ์ดไปหน้าได้เลย
- `FORTUNE_DISCLAIMER` ต้องหาเจอได้
- URL / back / refresh / เปิดลิงก์ตรงคงไว้
- ไม่สร้างราคา รีวิว คะแนน หรือข้อกล่าวอ้างใหม่
- ตัวเลขรีวิว 5.0 / 75,174 มีการยืนยันแล้ว แต่**ไม่แสดงบนจอแรก**

ยังไม่ทำจนกว่าจะอนุมัติ batch: เมนูทั้งหน้า, สรุปรีวิว, หน้าจ่าย, ภายในฟีเจอร์ (aspect / tarot / face / palm ฯลฯ)

ทุก batch ต้องคง URL, เงื่อนไขล็อก/กรอกข้อมูล, ราคาที่มีอยู่ และข้อความด้านล่าง ยกเว้นจะขออนุมัติตัดทิ้ง

| หน้า | ต้องคงไว้ |
|---|---|
| `/menu` | กลุ่ม «วันนี้» และ «เจาะลึก» · ชื่อ/คำโปรย/href/badge ของทุกแอปใน `MENU_GROUPS` · ล็อกพรีเมียม → ชีตจ่าย · ยังไม่กรอก → `/reading?next=` · `feature_open` แหล่ง `menu_paywall` / `menu_onboard` |

| `/reading/aspect` | งาน/เงิน/รัก/สุขภาพจาก pack · ทีเซอร์ล็อก · `from=premium\|menu\|reading` · ปุ่มกลับตาม `from` |

## Batch ที่เสนอ — รออนุมัติก่อนเริ่ม

แต่ละ batch เล็กพอให้ revert เป็นคอมมิตชุดเดียว และตรวจหน้าใน batch นั้นบวก regression ของชิ้นที่ใช้ร่วม

### Batch A (เสนอเริ่มเป็นชุดถัดไป) — `/menu` ภาษาภาพอย่างเดียว

- จัดเมนูให้เข้าต้นแบบนำร่อง: สี การ์ด มุม 18, `max-w-3xl`, เดสก์ท็อปไม่ล็อก 480
- **คงกดครั้งเดียว** สำหรับรายการที่เปิดได้ (เหมือนการ์ดฮับ)
- คง logic ล็อก → ชีตจ่าย และยังไม่กรอก → wizard
- ไม่ใส่ปุ่มกลางสองแตะ เว้นแต่จะอนุมัติแยกว่าแตะแรกโชว์อะไรที่กดตรงยังไม่มี
- ไม่แตะหน้าจ่าย รีวิว หรือภายในฟีเจอร์

ตรวจ: `/menu` มือถือ+เดสก์ท็อป, รายการฟรีไป URL จริง, รายการล็อกเปิดชีต, ไม่มีโปรไฟล์ไป wizard, แท็บเมนู, regression ฮับ/แท็บล่าง

### Batch B — `/reviews` ภาษาภาพ

- จัดหน้ารีวิวให้เข้าต้นแบบ
- สรุป 5.0 / 75,174 ได้เฉพาะหน้านี้ ถ้าอนุมัติ — **ไม่ใส่บน `/`**
- คงคำพูดใน `MAE_REVIEWS`

### Batch C — `/premium/pay` + ชีตจ่าย ภาษาภาพ

- ตารางเปรียบเทียบอยู่ในพับแรกที่อ่านได้
- คงราคา วิธีจ่าย Stripe และข้อความเปรียบเทียบ
- ไม่เปลี่ยน checkout

### Batch D — `/reading/aspect` ภายใน

- ภาพ/หัวข้อก่อน รายละเอียดใน `MoreDetails`
- คง id, `from`, ทีเซอร์ล็อก

### Batch E — `/reading/tarot` ภายใน

- จอเลือกไพ่ชัด ผลอยู่หลังจั่วสำเร็จ
- คง URL จากฮับ

### Batch F — `/reading/face` + `/reading/palm`

- ใช้เชลล์รายละเอียดร่วม
- คงสแกน / API / ล็อก ไม่เปลี่ยนโมเดลวิเคราะห์

### Batch G — ฟีเจอร์เจาะลึกที่เหลือ

- bazi, shirt, wallpaper, year, week, outlook, self-map, report, couple
- ทำทีละ 2–3 หน้าถ้าย่อยต่อได้ ถ้าชุดใหญ่เกินให้แยกก่อนลงมือ

**ไม่เสนอใน wave นี้:** login, dashboard, กฎหมาย, thanks, pricing, admin

## กติกาทุก batch (บังคับ)

- ใช้ design system ของนำร่อง
- รักษา functionality และเส้นทางเดิม
- ทดสอบ flow ที่กระทบ + regression ของ shared components
- ตรวจมือถือและเดสก์ท็อปจากหน้าที่ render จริง (360 / 390 / 768 / 1440 เมื่อทำ UI)
- รายงานตามสคริปต์ที่มีใน repo:
  - มี: `npm run lint` · `npm run build`
  - ไม่มี: สคริปต์ `typecheck` หรือ `test` — ถ้าต้องการเช็กไทป์จะรัน `npx tsc --noEmit` แล้วบอกว่านอกสคริปต์
- แยกบั๊กเดิมออกจากของที่เกิดรอบนี้
- ไม่แก้เรื่องนอกขอบเขต ไม่ push ไม่ deploy

## แผนวัดผล

### ระบบที่มีอยู่ตอนนี้

Event ใน `src/lib/analytics/events.ts`:

| Event | ใครยิง | ความหมายปัจจุบัน |
|---|---|---|
| `page_view` | ไคลเอนต์ ครั้งเดียวต่อเซสชัน | เข้าเว็บครั้งแรกในแท็บ |
| `screen_view` | ไคลเอนต์ ทุกเส้นทาง | เปิดหน้า |
| `feature_open` | ไคลเอนต์ เมื่อ path แมปฟีเจอร์ + เมนูล็อก/กรอก | เปิดฟีเจอร์ |
| `profile_saved` | เซิร์ฟเวอร์ PUT โปรไฟล์ตอนล็อกอิน | บันทึกโปรไฟล์บัญชี |
| `feature_complete` | เซิร์ฟเวอร์ หลัง `/api/fortune` สำเร็จ หรือสแกนหน้า/มือสำเร็จ | ได้ผลจริงจาก API |
| `pay_view` | ไคลเอนต์ หน้าจ่าย | เห็นหน้าจ่าย |
| `checkout_started` | เซิร์ฟเวอร์ | เริ่ม Stripe |
| `payment_succeeded` | เซิร์ฟเวอร์ | จ่ายสำเร็จ (กันซ้ำต่อ session) |
| `signup` · `login` | เซิร์ฟเวอร์ | สมัคร / เข้าสู่ระบบ |
| `thanks_line_cta` | ไคลเอนต์ | กดเพิ่มเพื่อน LINE |

ฟีเจอร์ id ที่มีอยู่: `home` `menu` `daily` `reading` `tarot` `shirt` `work` `money` `love` `health` `bazi` `face` `palm` `couple` `self-map` `year` `week` `outlook` `report` `wallpaper`

จุดที่ต้องรู้ก่อนเพิ่มของใหม่:

- Wizard ที่สำเร็จเรียก `/api/fortune` จึงมี `feature_complete` อยู่แล้ว
- ดวงวันนี้บนฮับ / aspect / ไพ่รายวันส่วนใหญ่คำนวณในเครื่อง — **ยังไม่มี `feature_complete`**
- ไม่มี event ตอนงานล้ม
- ไม่เก็บ device หรือแหล่งที่มา (utm / referrer)
- `feature_open` ทับกับ `screen_view` บนหลายเส้นทาง
- `profile_saved` ไม่ยิงตอนเซฟโปรไฟล์แค่ในเครื่อง
- ไคลเอนต์ส่งได้เฉพาะชุด `CLIENT_ANALYTICS_EVENT_NAMES` — `feature_complete` ต้องมาจากเซิร์ฟเวอร์

### Consent ที่มีอยู่

ไม่มีแบนเนอร์ยอมรับคุกกี้และไม่มีสวิตช์ปิด first-party analytics  
ที่มีคือลิงก์ `/privacy` `/terms` และนโยบายยังไม่พูดถึง event ในแอป, `visitorId`, Meta Pixel, หรือ LINE tag

รอบนี้: ไม่สร้างระบบ consent ใหม่ ไม่ตัดลิงก์กฎหมาย ไม่ใส่ชื่อ วันเกิด คำทำนาย หรือรูปสแกนใน analytics

### Event mapping ที่เสนอ (ใช้ของเดิมเมื่อความหมายตรง)

| จุดที่อยากรู้ | ใช้ event เดิม | สำเร็จคือ | ยังไม่พอ |
|---|---|---|---|
| 1. เข้าถึงหน้าหรือจุดเริ่ม | `page_view` (เข้าเว็บ) · `screen_view` (เข้าหน้า) | มีแถวตาม path | แยก device/แหล่งยังไม่ได้ |
| 2. เปิดฟีเจอร์หลัก | `feature_open` | เข้าเส้นทางฟีเจอร์ หรือเมนูส่งไปล็อก/กรอก | ไม่สร้าง `feature_open` ซ้ำถ้า tracker เส้นทางยิงแล้ว |
| 3. เริ่มทำงาน | ยังไม่มี event แยก | — | ใช้ `screen_view` `/reading` เป็นเริ่ม wizard · `pay_view` เป็นเริ่มจ่าย · หน้าฟีเจอร์ใช้ `feature_open` เป็นเข้างาน ไม่เสนอ `feature_start` จนกว่าจะแยก «เข้าหน้า» กับ «เริ่มทำ» ไม่ได้ |
| 4. ทำงานสำเร็จ | `feature_complete` · `profile_saved` · `payment_succeeded` | **ได้ผลจากเซิร์ฟเวอร์** ไม่ใช่แค่กดปุ่ม | ฮับ/aspect/ไพ่ท้องถิ่นยังไม่นับสำเร็จ |
| 5. เจอ error ที่ขัดขวางงาน | ไม่มี | — | ต้องมี event ใหม่ถ้าจะวัด |

### Schema ที่ขออนุมัติก่อนเพิ่ม tracking

ไม่ลงมือจนกว่าจะอนุมัติรายการนี้

**ไม่สร้าง** ถ้าอนุมัติให้ใช้ของเดิมอย่างเดียว: ไม่เพิ่มชื่อ event ใหม่ใน batch A–C

**ถ้าอนุมัติวัด error** (แนะนำรอหลังมี baseline):

```
name: feature_error          // ใหม่ — เซิร์ฟเวอร์เท่านั้น
feature: AnalyticsFeature    // id เดิม
props: { code: string }      // เช่น VALIDATION | UNAUTHENTICATED | AI_FAILED | PAY_CANCELLED
ไม่ส่ง: ข้อความ error ดิบ, ชื่อ, วันเกิด, ไฟล์รูป, คำทำนาย
```

ยิงเมื่อ API งานหลักตอบไม่สำเร็จ (เช่น `/api/fortune` 4xx/5xx, สแกนล้ม, checkout สร้างเซสชันไม่ได้)  
ไม่ยิงแค่ validation บนฟอร์มที่ยังแก้เองได้

**ถ้าอนุมัติแยก device / แหล่ง** (ใส่ใน `props` ของ `page_view` และ `screen_view` ครั้งแรกของเซสชัน):

```
device: "mobile" | "tablet" | "desktop"   // จาก viewport หรือ UA แบบหยาบ ไม่เก็บ UA เต็ม
source: string                             // utm_source หรือโฮสต์ referrer สูงสุด 64 ตัวอักษร ไม่เก็บ query เต็ม
```

ไม่ใส่ใน `feature_complete` ก็ได้ถ้า join ด้วย `visitorId` ที่มีอยู่

### วิธีเปรียบเทียบก่อน–หลัง

อย่าตั้งเป้าว่า redesign จะเพิ่ม conversion กี่เปอร์เซ็นต์ — ยังไม่มีตัวเลขตั้งต้นในแผนนี้

1. **ช่วงก่อน:** event จาก production ปัจจุบัน (สายหลัก) อย่างน้อย 14 วัน ถ้าข้อมูลน้อยให้ขยายเป็น 30 วัน
2. **ช่วงหลัง:** event ชุดเดียวกันหลังปล่อย v3 โดยยังไม่เปลี่ยนชื่อ event
3. **ตัวชี้วัดหลักจากของที่มี:**
   - เข้าเว็บ: นับ `page_view`
   - ลงมือกรอก: `screen_view` path `/reading`
   - ได้ผล wizard: `feature_complete` ที่ `feature=reading` (หรือ readingType จาก props ที่มี)
   - เปิดฮับ: `screen_view` `/premium`
   - เปิดเรื่อง: `feature_open` ของ work/money/love/health/tarot
   - เห็นจ่าย / เริ่มจ่าย / จ่ายสำเร็จ: `pay_view` → `checkout_started` → `payment_succeeded`
4. **แยก device และแหล่ง:** ทำได้หลังอนุมัติ props ด้านบน และมีข้อมูลครบทั้งสองช่วง  
   ช่วงก่อนไม่มี device/source ในแถวเก่า — เปรียบเทียบรวมได้ แต่แยกกลุ่มต้องรอเก็บใหม่
5. **อย่าเทียบ** จำนวน `feature_open` ดิบข้ามหน้าถ้าเส้นทางเปลี่ยนแต่คนยังทำงานเดิม (เช่น ฮับรวม daily+aspect)

### ข้อมูลที่ยังขาด

- จำนวน `page_view` / `screen_view` / `feature_complete` / จ่าย รายวันจาก admin analytics ของช่วงล่าสุด (ยังไม่ดึงในรอบนี้)
- สัดส่วนมือถือ vs เดสก์ท็อป และแหล่งเข้า
- สำเร็จของฮับ/aspect/ไพ่แบบไม่ผ่าน API
- error ที่ขัดขวางงาน

เมื่อมีเลขจริงจาก admin จึงค่อยพูดทิศทางได้ โดยไม่ตั้งเป้าเปอร์เซ็นต์ล่วงหน้า
